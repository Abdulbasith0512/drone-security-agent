Appendix A. Reproducing the results

1. Executive summary

What was built. A Python prototype of a drone security analyst for a fixed property. It takes scripted text-frame scenarios or real video, joins each frame to simulated telemetry, records what is seen as observations in a SQLite frame-by-frame index (with FTS5 search), merges repeated detections into temporal events, groups separate vehicle events into coarse “similar vehicle” entities, applies eight deterministic rules (four over camera events, four over drone telemetry) to produce evidence-linked alerts with severity ladders, recommended actions and a lifecycle, and lets an analyst answer questions and summarise the run with explicit citations to stored evidence. A scripted patrol and a video can both be processed progressively (each alert is saved the moment it fires), a read-only dashboard shows the stored evidence, and an offline, deterministic evaluation harness measures the components.

Core design. FRAME → OBSERVATION → EVENT → MEMORY → REASONING, with one rule: rules decide; the LLM only explains. Alerts, severities, events and entities come from deterministic code with configured thresholds. A language model (Gemini, through LangChain) can be used in two optional places only: as a vision model that describes frames, and as an analyst that explains stored evidence. It has no write access and cannot create, suppress or re-rate an alert, and its answers are shown only if a validator confirms that every cited id exists and was retrieved and that the facts it states in checkable forms agree with the cited evidence. A deterministic template analyst works with no key and is the fallback.

The bundled demo. 2. Problem statement

A docked drone patrols one property every day, but nobody watches hours of footage. The system must turn drone video and telemetry into a short, trustworthy list of things that matter (immediate alerts, such as a person loitering at the main gate), a searchable history (“show all truck events”, “did the blue pickup come back?”) and a short summary of the patrol. Two properties matter more than coverage: every alert and every answer must be traceable to the event, frame or telemetry evidence behind it, and the component that decides whether something is an alert must not be a language model that can be wrong in unpredictable ways.

The assignment asks for simulated telemetry and video frames, object and event logging with context, rule-based alerts, and a frame-by-frame indexing component, together with a feature specification, architecture and design artifacts, AI-generated components with an account of how AI was used, test cases for dynamic inputs and emergency responses, a report and demonstration videos. Section 4 maps each item to where it is met.

7. End-to-end data flow

7.1 The four ways data enters

  1. Scripted, batch: ingest (scenario YAML to observations and simulated telemetry in SQLite), build-events (observations to events and vehicle entities), analyze (rules to alerts). Each derived step replaces its own output in one transaction, so re-running is idempotent.
  2. Scripted, progressive: run --scenario NAME consumes telemetry and frames one tick at a time through the shared consumer; alerts are stored and printed as they fire.
  3. Video, batch: ingest-video samples, gates and describes frames (Gemini or a cassette) into observations; build-events and analyze derive the rest.
  4. Video, progressive: ingest-video --live sends each described frame through the same shared consumer as a patrol, so observation N, its events and any alert are in the store while the video is still being processed.

7.2 A worked trace (scripted security_events)

  1. Frames 1 to 9 are text observations of a person at the main gate (frame 5 has no detection). Each is joined to the nearest-prior simulated telemetry sample and stored with its zone, time and source.
  2. The aggregator merges them into one event, EVT-P-001, 480 s long: the one undetected frame is within the missed-frame tolerance, so it does not split the event.
  3. The loitering rule compares the event’s 480 s with the configured 120 s threshold and 300 s critical threshold and raises ALR-LOITER-EVT-P-001 as critical (an escalation of one alert, not two). Its reason, the compared numbers and the evidence frames (1–4, 6–9) are stored with it.
  4. The analyst answers “Show me the evidence for the loitering alert” from read-only tools, citing [alert:...], [event:...] and [frame:N]; every cited id is checked against the database before the answer is shown.
  5. The dashboard shows the same alert, its events and frames, and the same answer, read back from the stored run.

8. Video and VLM processing

  • VideoSource validates the file when it is opened: it exists and is non-empty, OpenCV opens it, the reported FPS is finite in (0, 1000], the frame count is positive, and the first frame decodes. Its identity is the SHA-256 of the file bytes.
  • Sampling is deterministic and time-based: sample k is taken at frame index floor(k × every × fps + 0.5) (default every 2 s), so the same video and settings always select the same frames.
  • Frame gate. The mean absolute difference between 64×36 greyscale copies of a frame and the last accepted frame is compared with a threshold (default 6.0, uncalibrated). The first frame is always accepted and the reference resets on a zone change. The gate is a pixel test: it is not motion detection, tracking or semantic analysis.
  • Carried observations. By default a skipped frame is represented by a copy of the last accepted observation, labelled <provider>+carried, so a static scene stays one continuous activity. A carried observation is temporal propagation of an earlier answer, not a new model inference. It is never carried forever: after --max-carry-seconds (default 300 s, the adaptive sampler’s bound) the provider is asked again.
  • Provider contract. A real model returns a strict ProviderOutput (description; objects with type, activity, coarse attributes and optional confidence). Unknown keys, wrong types and bad ranges are errors. The pipeline, not the model, assigns zone, time and identifiers.
  • Gemini FrameDescriber (official google-genai SDK). The frame is downscaled only if its longest side exceeds 1024 px, JPEG-encoded in memory (quality 85) and sent with shared instructions that tell the model to describe only visible objects and not to judge suspicion, intent, identity or severity. Native structured output is requested, then validated again by the project’s own strict parser; there is no regex extraction or silent repair.
  • Confidence. Gemini reports no calibrated probability, so none is requested. Objects are stored with a documented uncalibrated placeholder (0.5); it is not a probability and nothing downstream uses it for decisions.
  • Cassettes. Recorded responses are keyed by <video sha256[:16]>:<frame index> and hold descriptions and objects only (no images, keys or absolute paths). Modes: replay (no key, no API call; a missing frame is an error), record (calls the model only for frames not yet recorded and writes the file even if a later call fails) and live. A cassette recorded for another video, or by another model, is refused.
  • API key handling. GEMINI_API_KEY is read from the environment or a local, gitignored .env; it is never printed, logged or stored in the database, a cassette or a document. The dashboard and the bundled replay never read it.
The bundled recording. demo_assets/real_clip/ holds the clip ({{V.rv_bytes}} bytes, SHA-256 prefix {{V.rv_sha}}), a cassette of {{V.rv_entries}} recorded {{V.rv_model}} responses and a manifest that pins both files by SHA-256. The clip is licensed for redistribution and hosting in this demo, and the bundled replay needs neither the original source URL nor Gemini credentials. The dashboard refuses to build the run from a file that does not match the manifest.
No accuracy claim. Frame descriptions from Gemini are used as given. How accurate they are was not measured, because no annotated ground truth exists for the real clip (Section 19). The recorded runs show that the integration works, not that the descriptions are correct.

9. Telemetry integration

All drone telemetry in this system is simulated. A video file carries none, and the assignment asks for simulated telemetry, so the prototype produces it from a seeded simulator and treats the result as if the drone had reported it.

  • Simulator. A seeded patrol produces samples (time, latitude, longitude, altitude, zone, battery, optional signal) at a fixed interval (default 10 s) with a configurable battery drain (default 0.4% per minute), optional signal baseline and scripted dropouts; the same seed always gives the same samples. Scenarios and video timelines configure the patrol legs and the zone of each leg.
  • Video timelines. A video is given a simulated start time and either one zone for the whole clip (--start and --zone) or a timeline file with several zones. The timeline must cover the video. The CLI labels the row “SIMULATED telemetry samples (not from the video)”.
  • Association. Each frame is joined to the nearest-prior telemetry sample. The association stores the sample’s age and a stale flag when the age is strictly greater than 30 s. The frame inherits its zone and wall-clock time from the simulated clock.
  • Drone-safety rules (low battery, signal loss, altitude anomaly, geofence violation) read telemetry directly, with no camera needed, and also run progressively as samples arrive (Section 13). Their alerts carry the telemetry samples that support them as evidence.
  • Labelling. Simulated telemetry, time and zone are marked wherever they appear: in CLI output, in the analyst’s run limitations, and in the dashboard (a “SIMULATED” badge next to timestamps and telemetry).

  • Evidence chain. An alert links to events (and optionally an entity); an event links to observations; an observation is one frame. Any claim can be walked back to frame identifiers, which is what the analyst cites.
  • Timestamps are stored twice: the exact ISO-8601 text with its UTC offset and a fixed-width UTC string used for ordering and range filters, because comparing ISO strings with different offsets would order them wrongly.
  • Search safety. Search text is never passed to FTS5 as-is: each word is extracted and quoted and the words are ANDed, so input such as '; DROP TABLE x; -- is plain words. Results are ranked with BM25 and can be combined with time, zone and object filters. FTS5 has no synonyms (a search for truck does not find pickup) and no typo tolerance.
  • Integrity. Foreign keys are enforced; ingestion is one atomic transaction (a duplicate ingest is rejected and changes nothing); build-events and analyze replace their derived data in one transaction. Schema changes are additive and versioned with PRAGMA user_version; older databases are upgraded in place.
  • Why SQLite. One file, no infrastructure, transactional, and it supports structured filters and full-text search in the same database, so a frame, its objects and its search entry are written in one transaction. Embeddings and vector search were deliberately left out of scope.

Context memory

  • Events and entities are the system’s memory. Frames are never judged in isolation: the aggregator and linker keep the temporal and cross-event context, and the rules reason over it. The incremental context engine used by the progressive paths produces the same events and entities as the batch pipeline (a test asserts it).
  • The analyst’s conversational memory is separate and small: the last six question-answer pairs per session, in memory only (Section 16).

11. Event and entity construction

11.1 Temporal event aggregation

The aggregator is a streaming algorithm over chronological observations. It is temporal association, not object tracking: it never looks at pixels.

  • Detections of the same object type in the same zone join an open event when their stable attributes are compatible (person: clothing; vehicle: color, body_type; a value missing on either side is unknown). A detection with incompatible attributes starts a separate event, so two people standing together stay two events.
  • An event closes on a zone change, when the next matching detection is more than 180 s later, or after more than 2 consecutive frames in its zone without a matching detection (missed-frame tolerance: the drone looked, the detector missed). Otherwise it extends, keeping first seen, last seen, duration and ordered evidence.
  • One detection can join at most one event per frame; ties go to the most recently seen event. Event identifiers (EVT-P-001, EVT-V-001, …) follow first-seen order and are deterministic. Attributes are compared after normalisation (“dark blue” and “blue” agree); stored attributes keep their original text.

11.2 A close reason is not a departure

An event’s close_reason (gap, missed_frames, zone_change, scenario_end) says only why observation coverage of the event ended. Whether the object actually left is recorded separately in departure_observed_at (schema v6): it is set only when the drone kept looking at the same zone and the object was not there. A gap, a camera move to another zone and the end of the input say nothing about departure. This matters for loitering (Section 12), whose alert resolves only at the observed departure or when an operator resolves it. Older databases are not reinterpreted: re-running build-events fills the new column.

11.3 Coarse vehicle entity linking

  • Only vehicle events are linked, into entities such as ENT-V-001. Two events join when their normalised colour and body type are equal, they do not overlap in time, and the required attributes are present; missing evidence prevents a link and nothing is guessed. An explicit shared plate confirms an entity; conflicting plates never link.
  • Entities are labelled “similar blue pickup”. A coarse match is not physical identity, and no plate reading is performed. People are never identity-linked; there is no face recognition and no appearance model.

Known limitations (measured in Sections 19, 21 and 24): coarse matching can group different vehicles that share colour and body type; a vehicle described with inconsistent colours splits into two entities; free-text attributes from a real model fragment events; and the event model has no positions, so it cannot say which of several same-type objects in a frame is which.

12. Security and safety rules

Rules are deterministic functions over stored events, entities and telemetry, configured in config/security_rules.yaml. They decide whether an alert exists; no LLM takes part. Each alert carries a reason, the numbers the rule compared, and links to the triggering events, the entity (if any) and the frames.

  • Severity ladders and lifecycle. A rule may raise an alert at one severity and escalate the same alert when the condition worsens; the alert id never changes. Each alert has a status history (open, escalated, acknowledged, resolved), a confidence, a verdict and a recommended action written for the rule and severity (a fixed table entry, not model-written). Only a rule or an operator changes a status, never a language model.
  • Resolution. State alerts (loitering, safety) resolve when the condition ends; incident alerts (after hours, repeat vehicle, restricted zone) stay open until an operator acts. A loitering alert resolves only at the observed departure of the person (Section 11.2) or by an operator; the end of observation coverage does not resolve it.
  • Evidence. alerts --show <id> prints the reason, the rule facts and the evidence chain down to frames (or, for drone-safety alerts, telemetry samples). alert-action records an operator acknowledgement or resolution in the alert’s history.
  • Documented false positives and negatives include a delivery driver waiting at the gate (loitering), authorised night staff (there is no allow-list), a person missed for longer than the tolerance splitting into events that stay under the threshold, and thresholds that were hand-set on scripted data rather than validated on real footage.

13. Progressive / streaming processing

  • One consumer for every producer. ObservationPipeline is the single implementation of what happens to an observation once it exists. Both the scripted patrol engine (run) and the progressive video driver (ingest-video --live) hand their observations to it, so there is no video-specific event, entity or rule code. Telemetry joins the same way: a sample is stored, then the drone-safety rules run.
  • Progressive commits. Each step is committed and announced before the next frame is decoded and described, so observation N, the event it extends and any alert it raises are in the store while the input is still being processed. Ending the input closes open events as scenario_end and takes a last look with every rule.
  • Adaptive sampler (patrol engine). A frame is analysed on a scene change, a zone change, a telemetry change, an open event that has not been looked at for 120 s, or after 300 s without a call; otherwise the last observation is carried forward and labelled as carried. For scripted frames the scene signal is a multiset of (class, activity, attributes), so an activity-only change or an extra identical-looking object counts as a change.
  • Pacing and views. --speed sets simulated seconds per wall second (0 means as fast as possible); the live terminal view prints the alert lifecycle as it happens.
  • Batch equivalence. With sampling switched off the final database of a progressive scripted run equals the batch pipeline’s, and the progressive and batch video paths reach the same final events, entities and alerts; tests assert both.
  • What “real time” means here. It describes when things are computed on a simulated clock, not how good a description is and not a live feed; no live drone or RTSP stream was used.

15. LangChain analyst architecture

  • Boundary. The analyst may explain and summarise stored evidence. It cannot create, suppress or re-rate alerts, change event or entity links, or add observations: it has no write path (the tools are read-only methods, there is no SQL tool).
  • Why LangChain is confined. It is needed only to drive a tool-calling chat model. agent/llm.py is the only module that imports it; tools, citations, the session, the template analyst and the summary are plain Python, so the deterministic pipeline and the offline analyst run without the [agent] extra (langchain-core, langchain-google-genai; no LangGraph). Tests enforce the import rule.
  • Modes. ask and summarize take --provider offline|gemini|planner|replay. offline is the deterministic template analyst (no key); gemini is the LangChain + Gemini tool loop; planner is a scripted tool-calling stand-in (no LLM) that drives the real tool loop, caps and gates offline; replay replays recorded analyst turns from a cassette. The dashboard uses the offline template analyst.
  • The tool loop. With an LLM configured, a LangChain chat model (Gemini) runs a hand-written tool-calling loop bounded to 6 model rounds and 12 tool calls per answer. LangChain provides only the model and tool binding; there is no agent framework. The analyst model is configured separately from the vision model (ANALYST_MODEL).
  • System prompt. It requires: facts only from tools, inline citations, observation kept apart from inference, “similar” vehicle wording, no claim that the same person appears in separate events, no identity or intent claims, alerts reported exactly as stored, and “Insufficient evidence” when the evidence does not support an answer. A test checks that every tool a prompt names is registered.
  • Template (offline) analyst. Deterministic, pattern-matched and not language understanding: alerts by rule or id, events, entities, zone summaries, blue-pickup-style vehicle questions, after-hours people, objects, the run summary and a labelled keyword search; everything else gets “Insufficient evidence” plus the list of supported questions. Output is labelled “template answer (deterministic, no LLM)”.

16. Analyst tools and context management

  • Thirteen read-only, bounded tools: query_events, search_events, search_frames, get_event, get_frame, get_alert, get_evidence, entity_history, list_entities, list_alerts, telemetry_at, get_timeline, summarize_run. One name per tool (the run summary has no alias); invalid arguments return an error object instead of raising, so a model can correct itself. A few older methods remain only for the template analyst and are not offered to a model.
  • Bounds. Every result is capped (default 8 and at most 15 observations per search; 20 events, alerts or entities; 15 evidence observations per event; frame ids listed per event or alert capped; descriptions cut to 200 characters) and reports total, returned and truncated; a tool result over 12,000 characters is refused.
  • Sessions. A session keeps the last six question-answer pairs in memory (no persistence, no multi-user state) and passes them to the LLM. Template follow-ups such as “Where was it seen?” resolve a pronoun only when the previous answer named exactly one entity, alert or event; otherwise the answer is “Insufficient evidence” rather than a guess. ask --follow-up and --interactive drive a session from the command line; the dashboard keeps one server-side session per run.
  • Summaries. summarize renders bounded structured facts (counts, time span, zones, object counts, events with their alerts, entities, and data-driven limitations such as “telemetry is simulated” and “N observations are carried forward”); with an LLM the same facts may be rewritten as prose under the same gates. A follow-up is answered from stored evidence, never by reprocessing the video.
  • Truncation is never silent. Running the analyst on the first real-video recording showed that the template analyst silently dropped results (3 of 11 vehicle entities and 20 of 25 events). It now states what was cut (“showing 20 of 25 events, earliest first; 5 not shown”), lists the remaining entities briefly, and adds nothing when nothing was cut; answers that were not truncated were verified byte-for-byte unchanged.

17. Evidence, citations and factual-claim validation

Answers cite internal references with tokens such as [event:EVT-V-001], [alert:ALR-REPEAT-ENT-V-001], [entity:ENT-V-001], [obs:obs-10] and [frame:10]. An LLM answer is shown only if all of the following hold:

  1. every cited id exists in the database and was returned by a tool in this conversation;
  2. the answer cites something, unless it says “Insufficient evidence”; a refusal that follows a failed tool call is not accepted as “no evidence”;
  3. it contains no malformed token and no citation-shaped token of an unknown type (for example [evt:...]);
  4. it contains no identity or intent wording from a short phrase list (“the same person”, “burglar”, “criminal”, …), unless a negation cue stands in the same clause within eight words before it;
  5. the facts it states in checkable forms agree with the evidence cited in the same sentence (the factual-claim check below).

On failure the model gets one correction turn naming the problems; if the second answer also fails, or the model call fails, the deterministic template answer is returned instead, labelled as such. Each LLM-backed answer reports call metrics outside the answer text (model, rounds, tool calls, correction attempts, fallback yes or no, latency).

The factual-claim check

A citation proves that the evidence exists, not that the sentence around it is true: “The pickup was at the main gate [event:EVT-V-001]” cites a real event that happened in the parking area. agent/factcheck.py closes part of that gap deterministically. It reads claims out of an answer’s sentences with fixed, conservative patterns, anchors each to the evidence cited in the same sentence, and classifies it as supported, contradicted (the evidence has that fact and it differs) or unsupported (the cited evidence carries no such fact); only the last two fail validation.

  • Checked: alert severity, status and rule; zones; person and vehicle types; activities; clock times; durations; appearance counts; totals of alerts, events, observations and entities (with the filters the sentence itself states); object counts in a cited frame. Recommendations are not facts, but the premises inside them are checked.
  • Not checked, by design: anything not stated in one of those forms. This is not natural-language understanding or entailment, and no language model takes part; a claim phrased in a way the patterns do not recognise is simply not seen.
  • How it was hardened. Probing generated answers exposed false positives, all fixed before acceptance: query-window times, a clock time such as “12:03” read as the count 3, zone-scoped counts compared with store totals, observation counts on event lines, the closed-hours window and UTC offset read as times, double counting of [obs:] and [frame:], and ambiguous words such as “sat” and “no”. The citation validator itself was not weakened.
  • Measured boundary (Section 21): on the authored probe the citation check alone accepted all {{V.probe_unsup}} unsupported answers; with the factual-claim check the production gate rejects {{V.probe_prod_rej}} and still accepts {{V.probe_prod_acc}}.

19.3 Findings (documented for the first recording; the same effects appear in the bundled one)

  1. Event fragmentation from free-text attributes. Person events require the clothing text to match after lower-casing.   4. Carried observation. Frame 525’s objects are a copy of frame 450’s, so event durations that extend over it include propagation, not a new detection.
  5. No ground truth. The model’s descriptions were never compared with a human annotation.

20. Evaluation methodology

The evaluation harness (python -m drone_agent evaluate) is offline and deterministic: two full runs give identical functional results, it makes no model or network call, and every table in Sections 21 and 24 was generated by executable code and cross-checked against a fresh run when this report was built (the build fails if they differ).

  • Baseline is the production default. Ablations change one setting inside the harness (for example entities=[], a different max_missed_frames, gate threshold 0); production code is untouched.
  • No tuning against the fixtures. Thresholds were not adjusted to make results look better; the gate thresholds swept were chosen from the observed score distribution and the default stayed 6.0. Evaluation fixtures were not changed to improve any score, and negative results were kept.
  • Scripted detections do not measure perception. Fixtures are authored or generated, so results say whether the code behaves as designed, not how well a vision model sees. Labels (scenario expect: blocks) were written by the same author who wrote the rules.
  • The kind of evidence is labelled on every result: Controlled / synthetic, real video with recorded replay, automated tests or one-machine timing.

28. What could be improved with more time NOT IMPLEMENTED

None of the following exists in the repository; they are directions suggested by the measured limitations.

  • Stronger object identity and tracking. Bounding boxes and a tracker so that same-type objects in one frame can be told apart and event continuity is not inferred from text alone; this would also reduce the event fragmentation seen on real output.
  • Stronger entity resolution. Time-gap and plausibility constraints, more distinctive attributes and a faster linker (the measured superlinear stage), evaluated on labelled same-vehicle and different-vehicle pairs so that the false-link rate is measured and not only the contract.
  • Real telemetry integration. A real MAVLink or vendor feed in place of the simulator, with the timestamp, position and zone coming from the drone, and the rules re-validated against real signal and battery behaviour.
  • Richer temporal video summarisation. Summaries over longer patrols that group events into episodes and compare patrols across days, built on the same cited, validated evidence.
  • Better VLM evaluation with ground truth. Fixed-property footage with human-annotated objects, activities and events, longer clips and more than one vision model, so that perception accuracy, precision and recall can finally be measured instead of only integration; calibrated confidence and a gate threshold calibrated on real footage.
  • Authentication and production deployment. Authentication and authorisation, rate limiting, TLS, structured logging and monitoring, and hosted performance measurements, before any non-demo use.
  • Distributed storage and processing. A server database and queue-based ingestion for many drones and long retention, with the derived tables maintained incrementally, and paging in the analyst tools so large runs are answered completely.
  • Improved provenance and privacy handling. Recorded source, licence and retention metadata for every video, redaction of faces and licence plates before storage or display, access controls on footage, and a documented privacy review.
  • Broader claim validation. Extending the factual-claim check beyond its fixed forms, and measuring it against answers sampled from a real model instead of authored probes.

30. Conclusion

The prototype implements the requested pipeline end to end: simulated telemetry and video frames become indexed observations, temporal events, coarse vehicle entities and evidence-linked alerts from eight deterministic rules, raised progressively for a simulated patrol and for a video, and an analyst answers and summarises with citations that a validator checks against the database and facts that a deterministic check compares with the cited evidence. A real vision model (Gemini) integrates through a provider contract with cassette record and replay, a real clip is bundled with the repository and replays reproducibly with no key, and a read-only dashboard shows the stored evidence.

The evaluation shows what each component contributes and where it fails: the frame gate saves calls but is pixel-based and missed small meaningful changes on the fixture; missed-frame tolerance keeps one undetected frame from splitting a loitering episode; entity memory enables the repeat rule but can link different vehicles; the rules agree with authored labels on controlled scenarios; and the production gate rejects the claim forms it can read while still accepting {{V.probe_prod_acc}} of {{V.probe_unsup}} unsupported probe answers. The real-video replay validates integration and exposes event fragmentation and inconsistent model attributes.

These results are measurements on synthetic fixtures, one short real clip with no ground truth, and one machine. They do not establish real-world perception accuracy, security-detection performance, precision or recall, entity identity, semantic faithfulness of analyst prose, or production-scale behaviour, and the report makes no such claims.

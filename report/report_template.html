1. Executive summary

What was built. A Python prototype of a drone security analyst for a fixed property. It takes scripted text-frame scenarios or real video, joins each frame to simulated telemetry, records what is seen as observations in a SQLite frame-by-frame index (with FTS5 search), merges repeated detections into temporal events, groups separate vehicle events into coarse “similar vehicle” entities, applies eight deterministic rules (four over camera events, four over drone telemetry) to produce evidence-linked alerts with severity ladders, recommended actions and a lifecycle, and lets an analyst answer questions and summarise the run with explicit citations to stored evidence. It is driven from a command-line interface (a scripted patrol can also run progressively, raising alerts tick by tick), a small offline dashboard shows the stored evidence, and an offline, deterministic evaluation harness measures its components.

Core architecture. FRAME → OBSERVATION → EVENT → MEMORY → REASONING. Frames are never judged in isolation: observations are aggregated into events with duration, vehicle events are linked into coarse entities, and rules reason over events and entities. A frame-change gate avoids sending near-identical frames to the vision model, and a cassette layer records and replays model responses so that demonstrations and tests are reproducible without a key.

Deterministic rules versus LLM reasoning. Alerts, severities, events and entities are produced only by deterministic code with configured thresholds. An LLM (Gemini through LangChain) can be used in two places: as an optional vision model that describes frames, and as an optional analyst that explains stored evidence. It has no write access, cannot create, suppress or re-rate an alert, and its answers are shown only if a validator confirms that every cited id exists in the database and was actually retrieved. A deterministic template analyst works with no key and is the fallback.

What makes the approach useful. Every alert and every answer traces back to event, observation and frame identifiers; uncertainty is stated in the wording (“similar vehicle”, never identity); simulated telemetry, placeholder confidence and truncated lists are labelled where they appear; and each component has an ablation or a stated limitation.

How to read the results. Controlled synthetic experiments (Section 9) measure whether the pipeline behaves as designed on authored fixtures. The single real-video run (Section 10) validates end-to-end integration with real Gemini output on one short clip; it has no perception ground truth. Neither establishes real-world detection accuracy, and this report makes no such claim.

2. Problem definition and assumptions

A docked drone patrols one property. Nobody watches hours of footage, so the agent must turn drone video and telemetry into a short list of things that matter (alerts), a searchable history, and answers that show their evidence. The assignment asks for simulated telemetry and video frames, object and event logging with context, rule-based alerts, and a frame-by-frame indexing component, plus a feature specification, architecture, tests, a report and demonstration videos (coverage table in Appendix A).

Explicit assumptions
AreaAssumption
PropertyOne fixed property, one drone, one patrol per run; six zones: main_gate, driveway, parking_area, warehouse, restricted_zone, garage.
TelemetrySimulated: a seeded simulator (or a timeline you supply) produces position, altitude, battery and zone. A video carries none. An object’s zone is the drone’s zone when the frame was captured.
TimeVideo time is mapped onto a simulated wall clock, so time-of-day rules (for example crossing midnight) work on any clip. “Real time” means streaming aggregation on this simulated clock, not a live feed.
ObservationsScripted scenarios use authored text descriptions as deterministic ground truth for tests; real video is described by a vision model behind the same provider interface. Model output is treated as noisy.
IdentityNo face recognition and no personal identification. Vehicles are grouped only by coarse attributes (colour, body type) and always described as “similar”; people are never linked across events.
AccessThe core pipeline, tests and offline demonstrations need no API key or network. Gemini is optional and configured through environment variables only.
ScopeExplicitly out of scope: embeddings or vector search, YOLO or multi-object tracking, multi-drone, real MAVLink/RTSP integration, face recognition, Docker/CI, LangGraph. (The local read-only dashboard, battery and geofence rules and a 10K/100K benchmark were first postponed and later built.)

Design notes

  • Evidence chain. An alert links to events (and optionally an entity); an event links to observations; an observation is one frame. Any claim can be walked back to frame identifiers, which is what the analyst cites.
  • Timestamps are stored twice: the exact ISO-8601 text with its UTC offset (so the original timezone round-trips) and a fixed-width UTC string used for ordering and range filters, because comparing ISO strings with different offsets would order them wrongly.
  • Attributes are open-ended (whatever a model reports), so they are stored as canonical JSON and searched through FTS5; they are re-validated by Pydantic models when read back.
  • Search safety. Search text is never passed to FTS5 as-is: each word is extracted and quoted and the words are ANDed, so input such as '; DROP TABLE x; -- is treated as plain words. Results are ranked with BM25 and can be combined with time, zone and object filters. FTS5 has no synonyms (a search for truck does not find pickup) or typo tolerance.
  • Integrity. Foreign keys are enforced; ingestion is one atomic transaction (a duplicate ingest is rejected and changes nothing); build-events and analyze replace their derived data in one transaction, so they are idempotent. Schema changes are additive and versioned with PRAGMA user_version.

Why SQLite. One file, no infrastructure, transactional, and it supports structured filters (time, zone, object type) and full-text search in the same database, so a frame, its objects and its search entry are written in one transaction. It is enough for the assignment’s indexing requirement (“show all truck events”-style queries by time, zone, object or keyword); embeddings and vector search were deliberately left out of scope.

5. Vision and video pipeline

5.1 Video source, sampling and the frame gate

  • VideoSource validates the file when it is opened: it exists and is non-empty, OpenCV opens it, the reported FPS is finite in (0, 1000], the frame count is positive, and the first frame decodes. Its identity is the SHA-256 of the file bytes.
  • Sampling is deterministic and time-based: sample k is taken at frame index floor(k × every × fps + 0.5) (default every 2 s), so the same video and settings always select the same frames, including for fractional FPS. Frames are decoded sequentially, which is simple and codec-safe.
  • Frame gate. The mean absolute difference between 64×36 greyscale copies of a frame and the last accepted frame is compared with a threshold (default 6.0, uncalibrated). The first frame is always accepted, and the reference resets on a zone change. The gate is a pixel test: it is not motion detection, tracking or semantic analysis.
  • Carried observations. By default a skipped frame is represented by a copy of the last accepted observation, labelled <provider>+carried, so a static scene stays one continuous activity for the aggregator. A carried observation is temporal propagation of an earlier answer, not a new model inference. --skipped drop stores nothing for skipped frames instead.

5.2 Provider abstraction and Gemini

  • Provider contract. A real model returns a strict ProviderOutput (description; objects with type, activity, coarse attributes and optional confidence). Unknown keys, wrong types and bad ranges are errors. The pipeline, not the model, assigns zone, time and identifiers.
  • Gemini FrameDescriber (official google-genai SDK). The frame is downscaled only if its longest side exceeds 1024 px, JPEG-encoded in memory (quality 85) and sent with the shared instructions, which tell the model to describe only visible objects and not to judge suspicion, intent, identity or severity. Native structured output is requested, then the reply is validated again by the project’s own strict parser; there is no regex extraction or silent repair.
  • Retry and failure policy. Missing key, authentication failure, unknown model and rejected requests fail immediately (no fallback model). Rate-limit, timeout, network and server errors get at most two retries (2 s and 5 s); malformed output gets exactly one retry. The request timeout is 60 s. Error text is scrubbed of the key and the raw SDK exception is not chained. The model comes from --model, GEMINI_MODEL or a code default.
  • Confidence. Gemini reports no calibrated probability, so none is requested. Objects are stored with a documented uncalibrated placeholder (0.5); it is not a probability and nothing downstream uses it for decisions.
  • Cassettes. Recorded responses are keyed by <video sha256[:16]>:<frame index> and hold descriptions only (no images, keys or absolute paths). Modes: replay (no key, no API call; a missing frame is an error), record (calls the model only for frames not yet recorded, writes the file even if a later call fails, so a rerun resumes) and live. A cassette recorded for another video, or by another model, is refused.
  • API key handling. GEMINI_API_KEY is read from the environment or a local, gitignored .env; it is never printed, logged or stored in the database or a cassette.
No accuracy claim. Frame descriptions from Gemini are used as given; how accurate they are was not measured, because no annotated ground truth exists for the real clip (Section 10). The recorded Gemini runs show that the integration works, not that the descriptions are correct.

6. Event and entity reasoning

6.1 Temporal event aggregation

The aggregator is a streaming algorithm over chronological observations. It is temporal association, not object tracking: it never looks at pixels.

  • Detections of the same object type in the same zone join an open event when their stable attributes are compatible (person: clothing; vehicle: color, body_type; a value missing on either side is treated as unknown). A detection with incompatible attributes starts a separate event, so two people standing together stay two events.
  • An event closes on a zone change, when the next matching detection is more than 180 s later, or after more than 2 consecutive frames in its zone without a matching detection (missed-frame tolerance: the drone looked, the detector missed). Otherwise it extends, keeping first seen, last seen, duration and ordered evidence.
  • One detection can join at most one event per frame; ties go to the most recently seen event. Event identifiers (EVT-P-001, EVT-V-001, …) follow first-seen order and are deterministic.
  • Attributes are compared after normalisation (for example “dark blue” and “blue” agree, “grey” becomes “gray”); the stored attributes keep their original text.

6.2 Coarse vehicle entity linking

  • Only vehicle events are linked, into entities such as ENT-V-001. Two events join when their normalised colour and body type are equal, they do not overlap in time, and the required attributes are present; missing evidence prevents a link and nothing is guessed. An explicit shared plate confirms an entity; conflicting plates never link, even with identical coarse attributes.
  • Entities are labelled “similar blue pickup”. A coarse match is not physical identity; only a match level of confirmed (explicit equal plate evidence) says more, and no plate reading is performed.
  • People are never identity-linked. Separate person events stay separate, and the analyst may not say that the same person appears in separate events. There is no face recognition and no appearance model.

Known limitations (measured in Sections 9 and 10): coarse matching can group different vehicles that share colour and body type; a vehicle described with inconsistent colours splits into two entities; free-text attributes from a real model fragment events; and the event model has no positions, so it cannot say which of several same-type objects in a frame is which.

7. Security detection rules

Rules are deterministic functions over stored events, entities and telemetry, configured in config/security_rules.yaml. They decide whether an alert exists; no LLM takes part. Each alert carries a reason, the numbers the rule compared, and links to the triggering events, the entity (if any) and the frames.

The eight rules (default configuration)
RuleFires whenSeverity
Loiteringa person event in main_gate lasts at least 120 s (inclusive); the same alert escalates to critical at 300 smedium, then critical
After-hours presencea person event overlaps the closed window 22:00-06:00 (start inside, end outside; the window crosses midnight); time of day uses the event’s own UTC offset unless a property offset is configuredmedium
Repeat vehiclea coarse vehicle entity has at least 3 separate appearances; the wording is “a similar … was observed in N separate appearances” and says a coarse match does not confirm the same vehiclelow
Restricted-zone entrya person or vehicle event occurs in restricted_zonehigh
Low battery (telemetry)battery at or below 20%; critical at or below 10%; resolves once back at 25% or moremedium, then critical
Signal loss (telemetry)signal below 40% is degraded, below 15% is lost, and a gap of more than 30 s in delivered telemetry counts as a lost linkmedium, then high
Altitude anomaly (telemetry)altitude outside 5-120 m; beyond 2 m or 150 m it is highmedium, then high
Geofence violation (telemetry)the drone is more than 100 m from the property centre; critical beyond 150 mhigh, then critical
  • Identifiers and duplicates. Alert ids are deterministic, ALR-<RULE>-<subject or episode>, and an identical (rule, subject or episode) pair yields exactly one alert; re-running on unchanged data gives the same alerts.
  • Severity ladders and lifecycle. A rule may raise an alert at one severity and escalate the same alert when the condition worsens (loitering: warning at 120 s, critical at 300 s); the alert id never changes. Each alert has a status history (open, escalated, acknowledged, resolved), a confidence, a verdict and a recommended action written for the rule and severity. State alerts (loitering, safety) resolve when the condition ends; incident alerts (after hours, repeat vehicle, restricted zone) stay open until an operator acts, and only a rule or an operator changes a status, never a language model. A loitering alert also resolves when its event closes because the camera moved to another zone, which is a simplification: the last frame in the zone still showed the person. Different rules may alert on the same event because they describe different risks (a night-time loiterer yields a loitering and an after-hours alert).
  • Evidence. alerts --show <id> prints the reason, the rule facts and the evidence chain down to frames (or, for drone-safety alerts, telemetry samples).
  • Progressive processing. run --scenario NAME drives the same rules one tick at a time. Alerts are stored and printed the moment they fire, and with sampling switched off the final database equals the batch pipeline’s (a test asserts it for the two main scenarios). Only scripted scenarios run progressively; a real video is ingested first and turned into events and alerts by build-events and analyze.
  • Documented false positives and negatives include a delivery driver waiting at the gate (loitering), authorised night staff (there is no allow-list), a person missed for longer than the tolerance splitting into events that stay under the threshold, and thresholds that were hand-set on scripted data rather than validated on real footage.

8. Analyst agent

8.1 Tools and the tool loop

  • The analyst reaches the database only through thirteen read-only, bounded tools: query_events, search_events, search_frames, get_event, get_frame, get_alert, get_evidence, entity_history, list_entities, list_alerts, telemetry_at, get_timeline, summarize_run. There is no SQL or generic execution tool; invalid arguments return an error object instead of raising.
  • Every result has an explicit bound (default 8 and at most 15 observations per search; 20 events, alerts or entities; 15 evidence observations per event; descriptions cut to 200 characters) and reports total, returned and truncated.
  • With an LLM configured, a LangChain chat model (Gemini) runs a hand-written tool-calling loop bounded to 6 model rounds and 12 tool calls per answer. LangChain provides only the model and tool binding; there is no agent framework. The analyst model is configured separately from the vision model (ANALYST_MODEL).
  • The system prompt requires: facts only from tools, inline citations, observation kept apart from inference, “similar” vehicle wording, no claim that the same person appears in separate events, no identity or intent claims, alerts reported exactly as stored, and “Insufficient evidence” when the evidence does not support an answer.

8.2 Citations and the citation gate

Answers cite internal references with tokens such as [event:EVT-V-001], [alert:ALR-REPEAT-ENT-V-001], [entity:ENT-V-001], [obs:obs-10] and [frame:10]. An LLM answer is shown only if all of the following hold:

  1. every cited id exists in the database and was returned by a tool in this conversation;
  2. the answer cites something, unless it says “Insufficient evidence”;
  3. it contains no malformed token and no citation-shaped token of an unknown type (for example [evt:...]);
  4. it contains no identity or intent wording from a short phrase list (“the same person”, “burglar”, “criminal”, …), unless a negation cue stands in the same clause within eight words before it.

On failure the model gets one correction turn naming the problems; if the second answer also fails, or the model call fails (authentication, quota, network), the deterministic template answer is returned instead, labelled as such. Each LLM-backed answer reports call metrics outside the answer text (model, rounds, tool calls, correction attempts, fallback yes/no, latency).

What the gate is not. It checks form, existence and retrieval. It does not establish that the sentence around a citation is true, and it is not semantic entailment. Section 9.7 measures the resulting gap.

8.3 Offline template analyst, sessions and truncation

  • The template analyst is deterministic and needs no key. It pattern-matches a limited set of question shapes (alerts by rule or id, events, entities, zone summaries, blue-pickup-style vehicle questions, after-hours people, objects, run summary, a labelled keyword search) and otherwise answers “Insufficient evidence” and lists what it can answer. Output is labelled “template answer (deterministic, no LLM)”.
  • Sessions. A session keeps the last six question-answer pairs in memory (no persistence) and passes them to the LLM. Template follow-ups such as “Where was it seen?” resolve a pronoun only when the previous answer named exactly one entity, alert or event; otherwise the answer is “Insufficient evidence” rather than a guess. ask --follow-up and --interactive drive a session from the command line.
  • Summaries. summarize renders bounded structured facts (counts, time span, zones, object counts, events with their alerts, entities, and data-driven limitations); with an LLM the same facts may be rewritten as prose under the same gate. A follow-up such as “What objects were observed?” is answered from stored evidence, never by reprocessing the video.
  • Truncation transparency. Running the analyst on the real-video database showed that the template analyst silently dropped results (for example 3 of 11 vehicle entities and 20 of 25 events). It now states what was cut (“showing 20 of 25 events, earliest first; 5 not shown”), lists the remaining entities briefly, answers general people-and-vehicles questions for both categories, and adds nothing when nothing was cut; answers that were not truncated were verified byte-for-byte unchanged.

9. Experimental evaluation

9.0 Method and principles

The evaluation harness (python -m drone_agent evaluate) is offline and deterministic; two full runs produce identical functional results, and every table below was generated by executable code and cross-checked against a fresh run when this report was built. Principles:

  • Baseline is the production default. Ablations change one setting inside the harness (for example entities=[], a different max_missed_frames, gate threshold 0); production code is untouched.
  • No tuning against the fixtures. Thresholds were not adjusted to make results look better; the gate thresholds swept were chosen from the observed score distribution, and the default stayed 6.0. Negative results were kept.
  • Scripted detections do not measure perception. Fixtures are authored or generated, so results say whether the code behaves as designed, not how well a vision model sees.
  • Kind of evidence is labelled on every result. All results in Section 9 are Controlled / synthetic unless stated otherwise; they must not be read as real-world accuracy.

9.9 Streaming ground truth Controlled / synthetic

Question. Does a progressive run reproduce the events, alerts, severity ladders and timing that each scenario’s author wrote down beforehand? Method. {{V.gt_scenarios}} scenario files carry a machine-readable expect: block written before the system was run against them (camera scenarios such as a midnight loiterer, an intruder walking to the garage, a repeat pickup, a benign delivery and a flickering detector, and emergency scenarios for low battery, signal loss and a geofence violation). Each is run through the streaming engine with the default rules and the adaptive sampler on and matched one to one with its labels. F1 is 2TP / (2TP + FP + FN), so a scenario whose every prediction is wrong scores 0, not N/A.

{{TBL_GT}}

Measured. {{V.gt_exact}} of {{V.gt_scenarios}} scenarios matched exactly, with {{V.gt_tp}} true positives, no false positives and no false negatives over all expected alerts; the severity ladder, rung timing and final lifecycle status were all right. Detection latency is bounded by the frame spacing (60 s) for camera alerts and the 10 s telemetry tick for safety alerts. Limits. Labels and rules share an author and detections are perfect, so this shows the implementation matches its author’s intent, not real-world accuracy.

9.10 Adaptive sampling Controlled / synthetic

Question. Does combining pixel change, telemetry change, event state and a staleness bound detect more meaningful changes per model call than a pixel gate? Method. Eight seeded 600-frame generated streams with small, medium and large changes and illumination steps, using the real gate score and the real sampler. The saving is reported together with the changes missed.

{{TBL_SAMPLER}}

Reading. The previous pixel-only default avoided the most calls and missed the most meaningful changes; adaptive sampling bought recall with calls, and the fair comparison is a pixel gate with a fixed refresh. For scripted frames, which have no pixels, the sampler’s scene signal is a multiset of object class, activity and attributes, so an activity-only change or an extra identical-looking object counts as a change. Limits. Synthetic streams and an assumed 30% telemetry-cue rate; the adaptive sampler is used by the scripted runtime, while real video still uses the pixel gate alone.

10.1 Why there are zero alerts

None of the four camera rules could fire on this input (the run was recorded before the telemetry-safety rules existed, and its telemetry is simulated), for reasons unrelated to what the footage shows: loitering needs an event of at least 300 s in main_gate (the clip lasts 24.68 s and the longest event is 15 s); after-hours presence does not apply because the simulated start is 14:00 and closed hours are 22:00-06:00; the simulated zone is not restricted; and repeat vehicle needs three separate appearances (the maximum here is two). Zero alerts is not a security-detection result, not a specificity measurement and not evidence that nothing noteworthy happened. Any alert on this clip would equally be a consequence of the simulated time and zone, not of the footage.

10.2 Findings

  1. Event fragmentation from free-text attributes. Person events require the clothing text to match after lower-casing. Gemini’s wording varies (“dark clothing”, “dark coat”, “dark coat, jeans”, “dark jacket and jeans”, …), so most detections start their own event. A frame can hold up to three people and three vehicles and the observations carry no position, so which object is which cannot be inferred; an event unmatched for 3 consecutive sampled frames (9 s) closes. Result: 20 of 25 events are single-frame.
  2. Inconsistent VLM attributes. For example, frame 300 lists a white hatchback and a blue vehicle with no body type, frame 375 a blue hatchback and frame 600 a black hatchback; colour and body type are not stable descriptions of the same vehicle across samples.
  3. Coarse vehicle-linking limitation. The one multi-appearance entity links a “white van” at frame 0 with a white van at frames 375-525, 15 s apart; the frame-375 description calls it “a white ambulance” while its attribute says van. Whether it is one vehicle cannot be determined from this data. The system labels it a coarse, unconfirmed match; the case illustrates the false-link risk measured in Section 9.4.
  4. Carried observation. Frame 525’s objects are a copy of frame 450’s; three events extend over frame 525, so their durations (6 s, 3 s, 3 s) include propagation, not a new detection.
  5. No ground truth. Gemini’s descriptions were not compared with a human annotation.

10.3 Replay verification and analyst findings

Replaying the cassette (--provider cassette, no key, no API call) reproduced the run: 8 cassette replays, 9 observations and 33 objects, with observations and detected objects identical to the recorded run except the source label, which reads cassette instead of gemini:gemini-3.6-flash. The recorded artifacts (video, cassette, databases) stay under the gitignored output/real/ and are not part of the repository.

Asking the offline analyst about this run exposed the truncation described in Section 8.3. Before the fix, “What people and vehicles were observed?” returned 3 of 11 vehicle entities and no people, and the main-gate and objects answers listed 20 of 25 events with no note. After the fix they state “showing 20 of 25 events, earliest first; 5 not shown”, give full history for 3 of the 11 entities and list the other 8 briefly, and report both people and vehicles.

11. Scalability Measured on this machine

Method. Deterministic generated observations (empty stretches, people and vehicles that dwell for a few frames in a zone) at four sizes. Each in-memory stage was timed five times and SQLite queries twenty times; the median is reported. SQLite ingest and derived-table writes are single runs. No network or API call is involved, and the vision model’s latency, which dominates a real deployment, is not part of this benchmark.

{{TBL_SCALE}}

Measured. Event aggregation took a median {{V.p100_agg}} ms for 100 observations and {{V.p50k_agg}} ms for 50,000; rule evaluation {{V.p50k_rules}} ms and the keyword search (top 10) {{V.p50k_fts}} ms at 50,000. The empirical scaling exponent between the two largest sizes (time ~ sizek, k=1 is linear) was {{V.exp_agg}} for event aggregation, {{V.exp_rules}} for rule evaluation and {{V.exp_link}} for entity linking.

The entity-linking bottleneck. Entity linking is clearly superlinear at the largest sizes: {{V.p50k_link}} ms at 50,000 observations, longer than event aggregation. Reading the code, the linker recomputes each candidate group’s last-seen time (a maximum over the group’s events) for every comparison, which would explain the growth. This is an observation from the code, not a tested cause, and it was not fixed: the behaviour was preserved so the measurement stays a baseline.

{{SCALE_ENV}}
Limits. One machine and one session, synthetic observations with a small attribute vocabulary, in-memory stages that exclude reading rows back from SQLite. The results are measurements on this machine and make no claim of production-scale readiness, of behaviour on other hardware or with concurrent access.

14. Future work NOT IMPLEMENTED

None of the following exists in the repository; they are directions suggested by the measured limitations.

  • Stronger attribute normalisation for free-text model output (for example canonical clothing colour and garment classes) so events fragment less; this needs its own evaluation because merging different people affects loitering.
  • Object tracking with bounding boxes so that same-type objects in one frame can be told apart and event continuity is not inferred from text alone.
  • Improved entity matching: time-gap and plausibility constraints, more distinctive attributes, and a faster linker (the measured superlinear stage).
  • Paging for analyst tools so questions about large runs are answered completely instead of stating what was cut.
  • Calibrated vision confidence, or a documented way to obtain it, and gate-threshold calibration on real footage.
  • Broader real-world evaluation: fixed-property footage with human-annotated ground truth, longer clips, and more than one vision model.

17. Conclusion

The prototype implements the requested pipeline end to end: simulated telemetry and video frames become indexed observations, temporal events, coarse vehicle entities and evidence-linked alerts from eight deterministic rules (raised progressively for a simulated patrol), and an analyst answers and summarises with citations that a validator checks against the database. A real vision model (Gemini) integrates through a provider contract with cassette record and replay, and one real clip ran through the entire pipeline.

The evaluation shows what each component contributes and where it fails: the frame gate saves calls but is pixel-based and missed small meaningful changes on the fixture; missed-frame tolerance prevents one undetected frame from removing a loitering alert; entity memory enables the repeat rule but can link different vehicles; the rules agree with authored labels on controlled scenarios; and the citation gate rejects the categories it checks while accepting every citation-valid but unsupported answer in the probe. The real-video run validates integration and exposes event fragmentation, inconsistent model attributes and analyst truncation, one of which was fixed.

These results are measurements on synthetic fixtures, one short real clip and one machine. They do not establish real-world perception accuracy, security-detection performance, entity identity, semantic faithfulness of analyst prose, or production-scale behaviour, and the report makes no such claims.
